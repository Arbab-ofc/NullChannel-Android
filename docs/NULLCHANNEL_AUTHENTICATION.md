# NullChannel authentication

Guests retain the existing server-issued hashed anonymous session credentials. Registered accounts use Supabase Auth, validated with `auth.getUser()` for every authenticated HTTP request. Account identity comes exclusively from verification, never submitted IDs. Registered account cookies are separate from guest cookies: `nc_account_access` and `nc_account_refresh` (production uses `__Host-` prefixes). Cookies are HttpOnly, SameSite Strict, scoped to `/`, Secure in production. Origin middleware must run before account mutations.

`POST /api/account/signup` accepts username, email and password (12–128 characters). The v13 Auth insert trigger creates profile and defaults in the same database transaction. Supabase's configured email confirmation policy determines whether signup establishes a session. Registration errors are generic; email enumeration is not supported. Login returns profile and sets cookies. `POST /api/account/refresh` rotates tokens using the HttpOnly refresh cookie. `GET /api/account/me` restores profile; clients should attempt refresh once after an expired access token. Logout revokes the Supabase session and disconnects account sockets, removing matchmaking participation.

Password recovery redirects to the configured client origin `/reset-password`. The reset endpoint receives Supabase recovery credentials and the new password; credentials are validated by Supabase and never logged. Password changes require the current password. The recovery page must clear credentials from its URL immediately.

Profiles expose usernames, display names, optional avatar URL and bio through privacy-filtered endpoints; public social responses do not contain Auth IDs or emails. Self-profile responses include the account's own ID and privacy preferences. Username uniqueness is generated lowercase at the database layer. Updates are limited to one per 30 days by a database trigger, including concurrent requests.

The backend account endpoints require the versioned schema. Migrations v13–v22 were applied to the existing hosted project and checksummed. Actual signup-confirmation and recovery-email delivery still require a live mailbox/provider verification. Email delivery and redirects must be configured in the existing Supabase project's Auth settings. Production topology must remain same site for Strict cookies.

Account deletion requires current-password reauthentication, cancels matching, disconnects account sockets, destroys owned rooms and revokes memberships in other rooms, then deletes the Auth identity. Foreign-key cascades remove profile, privacy, requests, friendships, blocks and notifications. Each cleanup step must succeed before Auth deletion; retry is safe if an external dependency fails. Persistent avatar uploads use private ImageKit PNG/JPEG/WebP images up to 2 MiB. A separate durable intent is recorded before upload, and a transactional RPC commits profile metadata. Replacement/removal/account deletion queue the previous provider file through the existing retrying media cleanup queue. Avatar delivery streams through a privacy-authorized backend endpoint and disallows caching; provider URLs and file IDs are not exposed. Interrupted uploads are reconciled by `recoverAvatarIntents`.

Presence uses the existing Socket.IO server, not another server. The backend tracks individual tabs, and only the final disconnect removes the account matching lease. Clients send `presence:heartbeat` every 30 seconds; the server expires quiet tabs after 90 seconds. `presence:set` accepts online, away or invisible; invisible connections do not qualify for matching. Heartbeat handlers verify the connection credential and rate-limit updates. Presence payloads include username and filtered state, never last-active timestamps. Current per-tab aggregation is process-local: this deployment must use one Socket.IO process until shared tab aggregation is implemented. The Supabase matching lease supports restart recovery but does not make process-local presence aggregation multi-node safe.
